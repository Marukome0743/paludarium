### 2. Testing Posture への提案

**Methodology は `custom` に賛成します。** ただし Ordering の文を、層ごとに分けて一文で書けるようにすることを提案します。

- 提案する Ordering の文（面談で確かめる）：
  「命令・syscall・ゲストのプログラムは、実装の前にネイティブの x86-64 Linux で得た期待結果（基準ファイル）を用意して失敗を確かめ、実装してから通す。デコーダ・MMU・ELF の読み込み・仮想ファイルシステムなどの内部の層は、実装してからその層の単体テストを書いて実行する。」
- 理由：エミュレータの正しさの基準は外にある（ネイティブの CPU と Linux）。そのため「期待結果を先に」は自然に成り立ちます。一方、内部の層の単体テストまで先に書く TDD を全体に求めると、一人の開発では重くなります（推測）。

### 3. 差分テストの形（R1 の対策の具体化）

差分テストを 3 つの粒度に分けることを提案します。

| 粒度 | 何を比べるか | 基準の作り方 | 主に効く段階 |
|------|--------------|--------------|--------------|
| 命令単位 | 短い命令列を実行した後のレジスタ・フラグ・メモリ | Linux x86-64 上で命令列をそのまま実行して記録 | 段階 1〜2 |
| プログラム単位 | 標準出力・標準エラー・終了コード・syscall の列 | musl の static ビルドの小さな C プログラムをネイティブで実行して記録（syscall の列は strace などで） | 段階 1〜4 |
| 実行系どうし | JIT あり と JIT なし（インタプリタ）の結果 | インタプリタを基準にする（ネイティブは不要） | 段階 5 |

差分テストを壊れにくくするための注意（どれも推測。設計で確かめる）：

1. **基準ファイルはリポジトリに保存する** ことを勧めます。macOS（GitHub のホスト型ランナーは主に arm64 と理解しています。未検証）・Windows・wasm・手元の Windows 機では、ネイティブの x86-64 Linux の結果を作れません。基準ファイルがあれば、どのホストでも同じ期待値と比べられます。基準を作り直すジョブは Linux x86-64 のランナーで別に動かし、保存した基準とのずれを検出します。
2. **未定義のフラグを比べない**。x86 には結果が未定義のフラグや値があり（例：一部のシフトの OF、MUL の SF・ZF、入力が 0 の BSF の結果）、Intel と AMD で違うことがあります（ドキュメント根拠：Intel SDM の記述。手元では未検証）。命令ごとに「比べないビット」の表を持ち、基準ファイルには作った CPU の型番を記録することを勧めます。
3. **実行ごとに変わる値をそろえる**。getpid、時刻、getrandom、アドレス（ASLR）、スレッドの順番などは、比べる前にそろえるか、比べる対象から外します。エミュレータ側に「決まった値を返すモード」を持つかを設計で決めます。
4. **命令列を自動で作るテスト**（性質に基づくテスト、ファズ）を命令単位の差分テストに足すと、手で書いた例では見落とす組み合わせを拾えます。PR ごとではなく、夜間などに長く回す形を提案します。
5. **デコーダの正しさ**は、命令の長さとオペランドを既存の逆アセンブラ（llvm-objdump など）の出力と比べる方法があります。ただしこれは「外部の部品」の範囲（A1）に関わるので、テストだけで使ってよいかを面談で確かめます。

### 4. テストの層と量

Test Strategy は Standard（`aidlc-state.md`）なので、量と種類はそれに従い、ここでは中身の配分だけを提案します。

| 層 | 道具（候補） | 置き場所 |
|----|--------------|----------|
| 単体テスト | `cargo test`（実行は cargo-nextest でも可） | 各クレートの中 |
| 命令単位の差分テスト | 自作のハーネス＋保存した基準ファイル | 専用のテスト用クレートまたは `tests/` |
| プログラム単位の差分テスト | 自作のハーネス＋ゲストのバイナリ＋基準ファイル | `tests/` と基準ファイルの置き場 |
| 結合テスト（probe・aube） | 各段階の完了条件に合わせて実行 | `tests/` または別のジョブ |
| wasm（Node.js の Worker） | 起動用 JS＋自作のテストハーネス | JS 側のディレクトリ |
| wasm（ブラウザ） | ブラウザ自動操作の道具（候補：Playwright。手元には無い） | JS 側のディレクトリ |
| 速さの測定（段階 5） | 決まった入力で JIT あり／なしを複数回測る | 別のジョブ |

ゲストのバイナリ（hello world、小さな C プログラム、probe、aube）を **どう作り、どこに置くか** も決める必要があります。リポジトリに保存する場合は、作り方（musl の版、コンパイラの版）を記録して作り直せるようにすることを勧めます。

### 5. カバレッジ

- org.md の 80% 行カバレッジの下限は `mvp`・`feature` などのスコープ向けで、独自スコープ `rust-blink-port` には自動では当てはまりません（ドキュメント根拠：org.md の Testing Posture）。設けるかどうかは面談で決めます。
- 行カバレッジの道具は cargo-llvm-cov が候補ですが、手元には入っていません（検証済み：mise の一覧に無い）。測るのはネイティブの Linux だけにし、wasm ではカバレッジを測らない形を提案します（wasm での計測は難しいと理解しています。推測）。
- エミュレータでは、行カバレッジよりも **「範囲内の命令（SSE 系まで）のうち、差分テストが 1 件以上ある命令の割合」** の方が R1 に直接効きます。命令の表から自動で数えられるようにし、行カバレッジと並べて記録することを提案します。
- フラグの計算などの重要な部分に限って、ミューテーションテスト（候補：cargo-mutants。手元には無い）を時々回すことも選べます。PR のゲートにはしない提案です。
- 決めた下限は、Build and Test で下げてはいけません（org.md）。そのため、最初は低めに決めて段階ごとに上げる方が安全です。

### 6. CI の品質ゲート

GitHub Actions を前提に（C-E1、D16）、ゲートを 3 段にすることを提案します。

| ゲート | いつ | 内容 | 失敗したら |
|--------|------|------|------------|
| PR（マージ前） | push・PR ごと | rustfmt、clippy（警告はエラー）、Linux での単体テスト、保存した基準との差分テスト、3 つの OS でのビルドと単体テスト、`wasm32` 向けのビルド | マージしない |
| 段階のゲート | その段階に入ってから | 段階 2：Linux で probe・aube。段階 3：Node.js の Worker で probe・aube。段階 4：macOS・Windows で probe・aube | その段階に入った後はマージしない。入る前は参考表示だけ |
| 夜間・手動 | 定期 | 命令列の自動生成テスト、基準の作り直しとのずれ確認、ブラウザ 3 種、速さの測定、（行うなら）ミューテーションテスト | Issue にして直す |

補足：

- **3 つの OS の単体テストは段階 1 から PR のゲートに入れる** ことを勧めます。R3（Windows の syscall の対応付け）は後に回すほど直しにくくなるためです。probe・aube の合格を求めるのは段階 4 からで構いません。
- **wasm のスレッドの試作（D22）** の結果、`wasm32` のビルドを段階 1 から PR のゲートに入れられるかが決まります。
- **ブラウザのテスト** は、ページに COOP/COEP の見出しが要ります（C-T11）。テスト用のサーバーにそれを付ける必要があります。また、Playwright の WebKit は Safari そのものではありません。Safari の合格を「WebKit で代用してよい」とするか、「macOS 上の本物の Safari で確かめる」とするかを決める必要があります（推測。未検証）。
- **スレッドを使うテストは結果が揺れやすい**（tokio・rayon、futex、epoll）。時間切れの上限を決め、揺れたテストは記録して一定の期間内に直す決まりを提案します。
- **段階 5 の「JIT なしより速い」** は、そのままでは測り方が決まりません（inception.md：あいまいな言葉には数値の基準を付ける）。例：「決まった probe の入力で、各 N 回実行した中央値を比べ、JIT ありが X% 以上速い」のように、回数・統計量・差の大きさを要件分析で決めることを提案します。ホスト型ランナーは速さの揺れが大きいので、速さの判定は PR のゲートにしない提案です（推測）。

### 7. 規則への提案（discovered-rules.md）

- 「ALWAYS 差分テストで確かめる」は、そのまま固い規則にするなら、**「未定義の結果は比べない」** と **「基準はネイティブの x86-64 Linux で作った記録」** を添えることを提案します。添えないと、未定義のフラグで差が出たときに規則を守れなくなります。
- テストの素材にも C-T3・C-R2 が及ぶことを明記することを提案します。例：「NEVER jart/blink などのテスト用プログラムや期待値の表をそのまま写さない」。差分テストの素材を集めるときに写しやすいためです（R7）。人が述べた制約ではないので、規則にするかは面談で確かめます。

### 8. 面談で決めること（Testing Posture、リードの質問への追加）

リードの 5 問（Methodology、カバレッジ、基準の作り方、A1、ブラウザのテストの時期）に加えて、次を確かめることを提案します。

1. Ordering を「命令・syscall・プログラムは期待結果を先、内部の層は後」と層で分けて書いてよいか。
2. 差分テストの基準ファイルをリポジトリに保存し、手元（Windows）や macOS・Windows・wasm でも同じ基準と比べる形でよいか。基準を作り直すのは Linux x86-64 のランナー（または手元の WSL）でよいか。
3. 未定義のフラグや値を比べない扱いを認めるか。基準をどの CPU（Intel・AMD）で作るか。
4. カバレッジとして、行カバレッジに加えて「差分テストのある命令の割合」を記録するか。下限を設けるなら、最初の値と上げていく時期。
5. 3 つの OS の単体テストを段階 1 から PR のゲートにするか。probe・aube の合格を求めるのは各段階からでよいか。
6. Safari の合格を Playwright の WebKit で代用するか、macOS 上の本物の Safari で確かめるか。
7. 段階 5 の「速い」の測り方（回数、中央値か平均か、差の大きさ、どの環境で測るか）を、要件分析で数値にすることでよいか。
8. ゲストのバイナリ（hello world、C の小さなプログラム、probe、aube）を CI で毎回作るか、作ったものを保存するか。
9. 揺れるテストの扱い（再実行を許すか、記録して期限内に直すか）。
10. A1 の答えによって、テスト専用の道具（cargo-nextest、cargo-insta、cargo-llvm-cov、Playwright、逆アセンブラ）を使えるかが決まる。テスト専用なら使ってよいか。

### 9. 残る不確かさ

- 上の内容は、コードがまだ無い段階での提案です。道具の動作（cargo-llvm-cov の Windows 対応、Playwright の WebKit と Safari の差、GitHub の macOS ランナーの CPU）はどれも手元で確かめていません（未検証）。
- 未定義のフラグの例は Intel SDM の記述に基づくもので、実機では確かめていません（ドキュメント根拠）。

## Positions

- AGREE: 差分テストを Testing Posture の中心に置くこと。R1 に直接効き、範囲の文書の「検証」とも合う。
- AGREE: Methodology を `custom` にすること。期待結果を先に置く層と、単体テストを後に書く層が混ざるため。
- AGREE: Test Strategy は Standard のままにし、補足はそれに足すだけとすること。org.md の「下げない、足すだけ」と合う。
- AGREE: カバレッジの下限と道具を面談で決めること。独自スコープには 80% の下限が自動では当てはまらないため。
- OBJECT: 確認のコマンドを「ネイティブで動かした結果と比べる」とすること。開発機は Windows で、macOS・wasm でもネイティブの x86-64 Linux を動かせないので、保存した基準ファイルと比べる形にすべき。
- OBJECT: 「基準は Linux の x86-64 ランナーで作ります」を毎回の生成と読める書き方。基準はリポジトリに保存し、作り直しは別のジョブで行ってずれを検出する形にすべき。
- OBJECT: 「ALWAYS 差分テストで確かめる」を条件なしの固い規則にすること。未定義のフラグや値を比べない例外を添えないと、規則を守れない場面が出る。
- OBJECT: カバレッジを行カバレッジだけで考えること。エミュレータでは「差分テストのある命令の割合」を並べて記録しないと、R1 の残り具合が見えない。
